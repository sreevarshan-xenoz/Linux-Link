# Linux Link 2000+ Feature & Optimization Master Roadmap

Status: generated from the September 24, 2026 repository audit. Each numbered item is intentionally small enough to become an issue/spec/task. This roadmap is additive: items already implemented should be marked COMPLETE rather than reimplemented.

## Audit Baseline

The repository already contains a Rust workspace, Linux server, Android client/bridge, QUIC v2 work, Tailscale/ihror WAN work, screen/audio capture, adaptive bitrate, hardware encoder probing/fallback, persistent pairing/trust, multi-monitor/window capture, remote input, notifications, clipboard, files, WoL relay, privacy/view-only modes, session telemetry, on-device verification, and extensive planning documentation.

The main architectural direction is to consolidate control/media/input/file traffic around a versioned QUIC transport while keeping compatibility during migration. The roadmap below treats the existing implementation as the starting point and emphasizes verification, protocol hardening, performance, security, UX, extensibility, and product depth.

## Priority Model

P0 = correctness/security/ship blockers; P1 = core differentiators; P2 = important polish; P3 = advanced capability; P4 = experimental/research.

## How to Execute

1. Freeze the wire protocol with explicit version/capability negotiation.
2. Establish a real integration-test matrix: Hyprland, Sway, KDE Plasma/KWin, GNOME/Mutter, niri, X11, Tailscale LAN/WAN, relay, IPv4/IPv6.
3. Measure capture→encode→transport→decode→render latency separately.
4. Keep compatibility layers until v2 has deterministic migration and rollback.
5. Every feature gets unit tests, integration tests, failure tests, telemetry, docs, and a rollback path.
6. Prefer small commits and feature flags over large rewrites.

## Recommended Build Order

### Stage 0: Truth and Safety
Mark every existing item as COMPLETE/IN PROGRESS/PLANNED. Refresh README claims. Add one source of truth for protocol versions, supported transports, supported capture backends, and supported codecs.

### Stage 1: Transport Correctness
Finish unified QUIC migration cleanly, with explicit stream/datagram semantics, request/response correlation, congestion control policy, connection reuse, reconnect state machine, roaming, and compatibility tests.

### Stage 2: Media Pipeline
Prioritize true zero-copy capture, hardware encode/decode, 120Hz/144Hz/165Hz pacing, keyframe recovery, adaptive resolution/FPS/bitrate, and audio-video synchronization. Avoid premature AV1 work until H.264/H.265 paths are boringly reliable.

### Stage 3: Input + Desktop
Make input lossless where required, freshest-first where appropriate, stuck-key safe, multi-monitor aware, window-aware, and compositor-specific. Expand desktop control only after permissions and rollback are strong.

### Stage 4: Virtual Display
Build phone-as-monitor as a separate subsystem with its own display abstraction, EDID/profile management, compositor adapters, hotplug recovery, and clear fallback behavior.

### Stage 5: Productivity Platform
Macro engine, app-aware controls, window/workspace automation, media control, presentation mode, creator mode, and programmable shortcuts.

### Stage 6: Ecosystem
Multi-device orchestration, fleet management, plugin SDK, web diagnostics, Linux desktop integrations, packaging expansion, and community compatibility data.

### Stage 7: Hardening
Fuzz every parser. Add chaos testing for network, compositor, PipeWire, encoder, decoder, and Android lifecycle failures. Run long-duration sessions and recovery drills.

## Current High-Leverage Priorities

1. Correct README/release-state drift.
2. Finish and verify the unified QUIC architecture rather than maintaining two control planes indefinitely.
3. Implement/verify `ext-image-copy-capture-v1` where supported, while retaining PipeWire/portal and X11 fallbacks. The protocol is specifically designed to capture outputs/toplevels into client buffers and supports dmabuf constraints; current compositor support is uneven, so runtime capability detection is mandatory.
4. Separate transport fairness from media policy, especially for video, audio, input, and file streams.
5. Turn existing telemetry into a first-class observability subsystem with percentiles, timelines, and diagnosis.
6. Make recovery a product feature: reconnect, resume, retry, rollback, and human-readable explanations.
7. Treat security as architecture, not polish: scoped trust, capability permissions, secure secret storage, path confinement, command approvals, and audit logs.
8. Build virtual-display support only after capture, input, monitor selection, and hotplug behavior are stable.
9. Add benchmark gates so every latency/performance claim is measured on repeatable workloads.
10. Only then expand into plugins, automation, fleet management, and cross-platform clients.

## Architectural Principles

- One connection should carry logically separate traffic with explicit prioritization.
- Reliability should be selected per message class, not globally.
- Video prefers freshness; control/input/critical file metadata prefer correctness.
- Hardware acceleration must be runtime-verified, not inferred from compile-time capability lists.
- Every long-lived task must have cancellation, timeout, restart, and leak tests.
- Every privileged operation must have a clear capability boundary and visible user consent.
- Every fallback must be observable and actionable.
- Every protocol change must have a compatibility story.
- Every feature should degrade gracefully on lower-end hardware and weak networks.
- Do not add features simply because another product has them. Add them where they strengthen Linux Link's core promise: fast, native, private, reliable control of a Linux desktop from a personal device.

## Reference Notes

The QUIC architecture can legitimately exploit connection migration: QUIC connection IDs are designed to survive lower-layer address changes, allowing network-path changes without creating a completely new transport session. citeRFC9000

Wayland's `ext-image-copy-capture-v1` is the forward-looking capture protocol to evaluate for direct buffer capture; its current ecosystem support is not universal, so it should be implemented as a capability-selected backend rather than a single hard dependency. citeWaylandExplorer

The roadmap deliberately keeps experimental items marked as research rather than pretending they are shipping requirements.
